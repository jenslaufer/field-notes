# AutoMem — memory management as a trainable skill

Give the model file-system operations (`read`, `write`, `search`, `append`, `create`) in the
**same action space** as its task actions, then optimise only the memory side. Two automated
outer loops: a frontier meta-LLM reads complete episode traces and rewrites the *scaffold*
(code, prompts, file schema); then the agent's own good memory decisions become supervised
training data for a separate LoRA'd *memory specialist*, while the model that commits world
actions stays frozen.

## Setup

Inner model **Qwen2.5-32B-Instruct** (vLLM, local). Meta-LLM: **Claude Opus 4.6** for the
scaffold loop, **Opus 4.7** for the training loop, both `--effort max`. Three BALROG games —
Crafter (~10³ steps), MiniHack (8 tasks, ~10² steps), NetHack (10⁴–10⁵ steps). Metric:
progression rate, 10 fixed seeds [42…51]. Each scaffold revision is **gated**: kept only if
average progression on the *same* seeds strictly improves, one retry, else restart from a
clean session.

Behavioural deltas from scaffold optimisation alone (Figure 4): unproductive action rate
(stuck or oscillating) **−32 to −65 %**; redundant memory writes **−68 to −83 %**;
empty-search rate **−13 to −50 %**; per-step input context **−3 to −30 %** (−25 to −30 % on
Crafter and NetHack). The NetHack map file's per-step growth fell **138 → 6 characters
(−95 %)** after one change: replacing append-only logging with a coordinate-keyed
`<|UPSERT_MAP|>` that overwrites the entry for a tile instead of stacking duplicates.

Training internalised a **consult-before-write** discipline — writes per SEARCH in the LOG
phase: Crafter 0.84 → 0.39, MiniHack 2.89 → 0.82, NetHack 4.66 → 1.31 (−54 %, −72 %, −72 %).

## Where the abstract oversells

- **"Level with Claude Opus 4.5" holds on two of three games.** Crafter 51.36 vs 49.5 and
  MiniHack 30.0 vs 27.5, yes — NetHack **1.85 vs 2.0**, no. Against Gemini-3-Pro it loses on
  all three, on NetHack by 3.7×.
- **The 2–4× is measured against v0**, the file-system agent, not against the ordinary
  baseline. Against sliding-window it is Crafter ×2.63, MiniHack ×11, NetHack ∞/undefined
  (baseline 0.00).
- **The 32B result is bought with frontier compute, offline.** Two Opus models at max effort
  read complete traces (up to 10⁵ steps) and rewrite code. The cheap model is cheap only at
  *inference*.
- **Memory is episodic.** The file system starts empty every episode (stated in Limitations).
  Nothing here measures memory that survives *between* sessions.
- One scaffold and one specialist **per environment**; transfer is explicitly untested.

## Usable

The most transferable part is not the framework, it is **Appendix B — what the optimiser
actually changed**, because every entry is a deterministic scaffold rule, not a model
improvement:

- v5 Crafter: **before a craft/place action is committed, verify the materials exist and
  otherwise block it.** A precondition check in front of the model, identical in spirit to
  the Wix executability gate ([`2608.01050`](2608.01050-executability-gating.md)).
- Files the scaffold maintains *programmatically* from the observation (`inventory.txt`,
  `current_status.txt`) so the model never reconciles its own records.
- A pre-populated strategy file so early steps are not spent rediscovering the goal.
- Deduplicating key on the fast-growing file (the map), so it stops growing.

**→ hier:** the closest published description of what `state/memory/` is. But the claim it
supports is narrower than it looks: *scaffold* beats *model*, on episodic memory, when a
frontier reviewer reads whole traces. The parts that port directly are the four scaffold
rules above — especially the deduplicating key, which is the same lesson as the
`waiting.md`/`routines.md` condensations (the file that grows is the one that needs a key,
not more discipline).
