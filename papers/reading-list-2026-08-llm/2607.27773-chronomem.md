# ChronoMem — an undo button for agent memory, and how far it actually gets

Existing agent memory is **forward-only**: it accumulates, consolidates and overwrites, with
no way to inspect or revert. ChronoMem adds a version-control layer inside Google's Agent
Development Kit: every memory write commits a **whole-memory snapshot**, versions are indexed
by a semantic commit descriptor, and a natural-language "undo" request is resolved to a
concrete version and restored deterministically.

## Design

- **State model**: append-only event log + materialised snapshots + a `HEAD` pointer, in
  SQLite. Log-plus-snapshot avoids replaying the log on rollback (storage traded for restore
  speed). Explicit event-sourcing/ARIES lineage.
- **Interface invariant**: after rollback to `v*`, every subsequent read is scoped to `v*` —
  no post-`v*` visibility. This is the part prompting cannot give you.
- **Semantic commit descriptor** per version: `{delta, summary, op, labels}`. Retrieval runs
  over these descriptors, **not** over snapshots or raw events, so selection cost scales with
  the number of commits and is independent of memory size.
- **NL → version**: BM25 via SQLite FTS5 ∥ dense retrieval, fused with Reciprocal Rank Fusion
  (k₀ = 60), then a cross-encoder rerank (Cohere Rerank-3.5).
- **Rollback** truncates versions after the target — Git `reset`, not `revert`.

**Post-exposure protocol** (the real contribution): ingest the full stream to `v_T`, *then*
ask to roll back, then run the task. The agent has already seen the later information and must
behave as if it never arrived.

## Read the absolute numbers, not the deltas

- **Recall@1 = 20.5 % on LoCoMo.** The system picks the intended version correctly one time
  in five. The abstract's "strong recovery on semantic version selection" is true only
  relative to a 12.0 % hybrid baseline. Rollback targeting is *not* solved here.
- **Prompt-only rollback is near zero (0.9–2.8 % F1).** This is the paper's most solid
  result and it is a negative one: once the model has seen the later information, telling it
  to ignore that is worth almost nothing. Counterfactual behaviour is an **architectural**
  property.
- **Internal inconsistency:** §5.1 prose reports MAB improving "24.3 → 39.4 % Recall@1,
  53.8 → 65.2 % Recall@5", while Table 3 gives **33.4 %** and **60.2 %**. The tables are the
  lower and presumably correct figures; the prose is the number that would get quoted.
- Full-history prompting beats retrieval-only on MAB summarisation but loses on LoCoMo QA —
  the two baselines swap order by task, which is worth noticing before generalising either.
- Limitations conceded: **linear history only** (no branching or merging), SQLite serialises
  writes and concurrency is never evaluated, and rollback queries are generated from
  ground-truth anchors so their distribution is not real user intent.

**→ hier:** the snapshot half of this is already free — `state/` is a git repo, and git gives
branching, which ChronoMem explicitly lacks. What is missing here is the semantic half,
finding *which* past version to return to. The measured 20.5 % Recall@1 is the argument for
**not** building that: at this quality a natural-language version picker would be wrong four
times in five, while `git log -S '<the wrong fact>'` is exact. The result to keep is the
negative one — "just ignore what you read later" scores 2 %; if a fact has to be revoked, it
has to be revoked in the file, not in the instruction. Same shape as
[[retraction hits generator]].
