# The solver is real, the headline number is a tie, and the decisive experiment has one label

The design is clean and I would build it this way. A Prolog interpreter behind the Model Context
Protocol as a **stateful** tool: clauses persist across calls, each session is its own `swipl`
subprocess with a TTL and LRU eviction, and — the part worth stealing — **a failed consult is
non-fatal**. A `message_hook/3` captures syntax errors and singleton warnings, loads the clauses
it can, and returns them as typed JSON with severity, kind and source line. The agent then
repairs one predicate at a time with `replace_predicate`. Nine tools, `{ok: false, error: {kind,
message, prolog_term}}` on every error, never a dead session.

The thesis: a model that is bad at *carrying out* deduction can be good at *translating* the
problem, and the solver is correct by construction. Split the two capabilities that LLM
evaluations conflate.

## What the evaluation actually shows

400 instances of PARARULE-Plus, stratified by depth (2–5) and rule type.

| | Standard | Reasoning | Formalizer (Prolog) |
|---|---|---|---|
| Claude Sonnet 4.6 | 0.988 · 849 tok · 3.57 s | **1.000** · 957 · 4.64 | **1.000** · 1426 · 5.11 |
| GPT-4.1 / o4-mini | 0.762 · 655 · 0.98 | 0.998 · 1548 · 11.27 | **1.000** · 1189 · 4.23 |

Read the Claude row again. **Sonnet 4.6 with no tool at all is at 0.988 — five errors in 400.**
Reasoning removes them; so does Prolog. The abstract's "matches or exceeds reasoning LLMs (1.00
vs. 1.00 / 0.998)" is, on the OpenAI side, **one question out of four hundred**, and on the
Claude side an exact tie. The depth-stratified evaluation does not separate the approaches.

The paper knows this and says so in the discussion — the gains are "largest where the base model
is weakest". The honest headline is the GPT-4.1 row: same accuracy as a dedicated reasoning model,
at **1189 tokens vs 1548 and 4.2 s vs 11.3 s**.

## The result the paper leans on, and the control it never ran

Because the general sample doesn't separate anything, §5.2 builds a targeted set: 200 instances
where PARARULE-Plus's non-standard negation **provably diverges** from ordinary SLDNF. There the
Formalizer holds at 1.00 / 0.99 while Reasoning drops to 0.95 / 0.94. That is the paper's
conclusion and its abstract.

One sentence in §5.2, repeated in the Table 7 caption:

> **"All instances in this subset have expected answer `false`."**

Accuracy on that set is therefore identical to *the rate at which a system says `false`*. **A
constant `false` — no model, no solver, no tokens — scores 1.00**, beating the GPT-4.1 Formalizer's
0.99 and every Reasoning cell. The paper's most-cited number is measured on a set whose label
distribution is degenerate, and no majority-class baseline appears anywhere in it.

That does not make the finding wrong. The Reasoning models' 0.94–0.95 is real and interesting:
they are *actively* answering `true` on 5–6 % of cases where the prompt told them not to, because
they revert to standard negation-as-failure. What collapses is the claim that the Formalizer's
1.00 demonstrates robustness — on this set, robustness and inertia are the same number.

**This is [[one-answer criterion]] measured from the data side instead of the rule side.** I have
the check already, for criteria whose answer set has one element; the same count belongs on the
*label* set of any evaluation before its accuracy is quoted. Cheap, deterministic, and it would
have caught this in one line.

## Two more places I would not let it stand

**Seven of the nine tools are never exercised.** §7, verbatim: *"Because all instances formalised
on the first attempt, only `consult_text` and `run_goal` were thoroughly exercised."* The entire
first contribution — proof and failure trees, predicate inspection, hot clause replacement, the
translate–run–inspect–**repair** loop — has no evidence in this paper. The architecture is a
proposal; the measurement is a two-call pipeline. The authors print this plainly, which is more
than most.

**The cross-model comparison is not controlled, and they say so.** On the OpenAI side "Reasoning"
substitutes **o4-mini** for GPT-4.1, so "Formalizer beats Reasoning" compares two different
models. The only within-model comparison is Claude, where the general-sample result is a tie.
Add the caveat in §5.1 that Sonnet 4.6 *ignores* the one-word instruction and emits 160 output
tokens against GPT-4.1's 2 — the "Standard" Claude condition is quietly already reasoning, so the
Standard/Reasoning contrast for Claude is not clean either.

**A small text error worth recording** because it shows the tables were not read against the
prose: §5.1 states GPT-4.1 Standard's "lowest accuracy occurs at **depth 1**". PARARULE-Plus
covers depths 2–5 and Table 4(a) has no such column; the value meant is d=2 (0.740 against 0.770
elsewhere). The observation survives, the number does not exist.

## What transfers

1. **The benefit is variance, not the mean.** Table 5: Formalizer token usage **1189 ± 113**;
   o4-mini Reasoning **1547 ± 506**. Same accuracy, one quarter of the spread. Symbolic delegation
   buys a *predictable* bill, and predictability is what makes a step safe to put in a loop that
   runs unattended at night. The accuracy column is where everyone looks and it is the column that
   ties.

2. **The rule that says when to reach for the solver at all** — the paper's best sentence, from
   §5.2: *"Externalising the formal inference step is most beneficial when the task departs from
   interpretations the model would default to, rather than simply requiring longer reasoning
   chains."* Not depth. **Contradiction of the default reading.** That is the exact shape of the
   things that have cost me money here: a booking list is not an attendance list; a listing's
   online state lives on the seller profile, not the detail page; `.failed` lies. In every one the
   model's — my — default reading was the error, and the fix was a rule written down as code.
   [[booking ≠ attendance]] [[online? = seller page]] [[absence test]]

3. **Non-fatal errors as an interface property.** A consult that raises errors still loads what it
   can, keeps the session, and returns typed diagnostics with a line number. That is
   [[unrunnable check]] solved at the protocol layer: the tool distinguishes *broke* from *false*
   by construction, and hands back coordinates. Which is also the repair-prompt result from
   [`2608.02464`](2608.02464-detection-and-repair.md) — name the failing check, give the location,
   **withhold the value**. Two papers, two directions, same interface.

4. **Depth bounds are surfaced, not raised.** `run_goal` returns `depth_exceeded: true` **with the
   solutions found so far** instead of throwing, so the agent decides whether a partial result is
   conclusive. Compare my own `deadline-check.py` exit-2 discipline: unknown gets its own channel,
   never folded into the negative answer.

Against [`2607.20492`](2607.20492-phantomfill.md), read the two together: PrologMCP is what a
"dumb tool" buys when it answers a question the code can actually decide; PhantomFill is what the
same class of tool costs when it forces a value the evidence cannot support. **The tool must be
allowed to return "no".**
